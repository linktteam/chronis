# WP10B replay of the A3 safety demonstration on a subset (2026-11-27)

Every number: Python 3.12.3, repo pins (numpy 2.2.6, scipy 1.15.3), the development 2-core AVX-512 machine (OpenBLAS kernel SkylakeX). Criteria: `tests/PREDECLARED_CRITERIA_WP10B.md` section 14, committed (afeb4ec) before any replay fit existed. Words: RUN, READ, INFERENCE, UNKNOWN.

## What opa runs
`PYTHONPATH=. python integration_report/wp10b/scripts/a3_safety_replay.py run --out OUTDIR --workers N` (add `--users-per-stratum 1` for a smoke run). Needs the repository checkout (it reads `tests/DESIGN_FREEZE_WP10A_A3.txt` and the stored fits `wp10a_evidence/a3_eval_fits.jsonl`, 16 MB, both tracked) and the repo-pinned 3.12 environment. It sets one BLAS thread per worker. Stop and restart with the same command: finished fits and users are skipped. `summary --out OUTDIR` prints the totals of what exists so far (marked PARTIAL until all 36 users are done); `reference` prints the numbers of the stored fits alone (seconds, no fitting).
- **What it does:** 12 users per stratum (SAFE-EXTRA users 10151..10162 hard, 10171..10182 medium, 10191..10202 easy), single seed (weekly seed-A chain, windows [0, t) for t = 90, 97, ..., 146, 150, fit seed = user): 360 fits of the baseline engine, K = 3, 60 iterations, 10 restarts, by the same function that made the stored fits; replay through the production lineage at the chosen point (flag ON, sharpness 0.95, h = 2.5; refused if the freeze file says otherwise); counts gate-eligible alignments, served ones, wrong-and-unflagged ones; compares every fit with the stored one in the discrete outputs.
- **Partial results:** after every user a line goes to `OUTDIR/users.jsonl` and the running totals are printed; every fit goes to `OUTDIR/fits.jsonl` as it finishes. `OUTDIR/env.json` records the machine (platform, CPU flags starting with avx / fma / sse4, numpy, scipy, the BLAS architecture).

## Time (stated before the run; RUN estimate from the stored fit times)
The 360 fits of these 36 users took 5931 s in all when WP10A made them (mean 16.5 s, median 14.7 s, maximum 53.5 s): about **99 CPU-minutes**, so about 99 / workers minutes of wall clock on a quiet machine (two workers about 50 minutes, four about 25). RUN, the 3-user smoke here: 30 fits, 257 s of fit time (mean 8.6 s; these three users are cheaper than the average), 264 s wall with one worker beside the running background queue. A 7763 may be faster or slower: UNKNOWN.

## What would count as failure (declared before any fit; criteria 14.3)
1. **SAFETY FAILURE:** any wrong-and-unflagged alignment. The stored fits of these 36 users give **0 in 324** alignments (167 served: hard 8/108, medium 73/108, easy 86/108; one-sided exact 95% upper bound 0.92%; `wp10b_evidence/replay_reference_36users.txt`); WP10A pooled: 0 in 972. An upper bound above 1% (fewer than 299 alignments) is reported, not a failure: this is a transfer check on a subset, not a new per-stratum demonstration (per stratum, 108 alignments give 2.7% at best).
2. **REPRODUCTION FAILURE:** a fit whose discrete outputs differ from the stored fit (worked or not; state, collapse flag and iteration count of each of the 10 restarts; index and labels of the selected restart), or a window whose lineage state, served flag or correctness differs from the replay of the stored fits. Expectation (INFERENCE): no difference on an AVX-512 runner; none on a 7763 either, from the 12-user cross-machine battery (24/24 discrete outputs identical with numpy's AVX-512 dispatch off) and the three-kernel tolerance of WP10A A2; the replay is a stronger test than either, and a difference is a finding.
3. Only reported, no verdict: restart log-likelihoods differing by more than a relative 1e-6.

## Result of the smoke run here (RUN; not the demonstration)
3 users (10151 hard, 10171 medium, 10191 easy), 30 fits: 27 alignments, 10 served (0, 1, 9), **0 wrong-and-unflagged**; all 30 fits identical to the stored fits in every discrete output, 0 lineage-state differences, largest relative log-likelihood difference 0 (bit-identical, the same machine and kernel). The verdict lines read `SAFETY: no wrong-and-unflagged alignment in 27; one-sided exact 95% upper bound 10.50% (ABOVE 1% ...)` and `REPRODUCTION: the discrete outcomes of all 30 fits ... are identical`. This shows the script works end to end and the fits are reproducible on the machine that made them; it says nothing about another CPU. Files: `wp10b_evidence/replay_smoke_3users/`. I have not run the full 36-user replay here (about 50 minutes of both cores while the background queue is running); I run it if the owner asks.

## A bug I found while writing it (fixed before any replay run)
`wp9_replay_lib.prepared` caches by (user, seed, window, ...) and NOT by the contents of the fit record. In my first version the replay of the stored fits followed the replay of the new fits in the same process, so it silently reused the new fit and the lineage-state comparison compared a fit with itself (it would always have said "no difference"). A planted defect (a failed fit, a swapped planted truth) showed zero differences, which is how I saw it. The cache is cleared before each replay (`replay_chain`), the end-to-end tests plant a wrong alignment (1 wrong-and-unflagged, 1 state difference) and a failed fit (a missing step, 1 state difference), and mutant R17 (the cache not cleared) is caught.

## Limits
