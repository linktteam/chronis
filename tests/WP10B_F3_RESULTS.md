# WP10B F3 results (2026-11-27): a crashed or malformed assessment is never ALIGNED

Setting for every number: Python 3.12.3, repo pins (numpy 2.2.6, pandas 2.3.3, scipy 1.15.3, scikit-learn 1.9.1, pytest 9.1.1), the same 2-core AVX-512 machine as the rest of WP10B. Criteria: `tests/PREDECLARED_CRITERIA_WP10B.md` section 12 (Part 6), committed before any code change, with dated corrections in 12.8. Words: RUN = I ran it here; READ = I read the code; INFERENCE; UNKNOWN.

## What changed (RUN: the tests below pass)
- `backbone/hssm/lineage.py`: `step` now collects every crashed or malformed assessment of a fit (stages `k_change`, `fit_stability`, `scaler`, `matching`) and gives **CONTINUITY_UNVERIFIED** with the reason **`assessment_crashed`** and the old names kept; `may_claim_same_as_before` is False. The same reason is added on the first fit and on the K-mismatch path (K_CHANGED); those were never ALIGNED. A crashed fit is not promoted to the anchor.
- `backbone/hssm/k_change.py`: `assess_k_change` and `assess_against_anchor` no longer return `suspected = False, reason = "assessment_error"`; they return `reason = "assessment_crashed", crashed = True, error_class = <class name>` and nothing from the message. `fit_recent_window` returns `None` only for `FittingConvergenceError` and `ColdStartError` ("did not finish", no signal); any other exception propagates to the assessment, which records it as a crash.
- `backbone/hssm/alerts.py`: new kind `ASSESSMENT_CRASHED`, `emit_once` (at most one alert per kind, user and key in this process, memory bounded at `DEDUP_MAX = 50 000` triples, oldest forgotten first), `exception_class_name` (identifier characters only, at most 80, else `Exception`).
- Alert fields (exactly): `user_id_hash`, `stage`, `data_revision_id`, `reason` (= `assessment_crashed`), `error_class`. No message text, no traceback, no data values (T7 plants a distinctive string in the exception message and checks the alert, the log record and the lineage record). One alert per (user, stage, data revision); a crash with no user id or no revision id cannot be deduplicated and is always emitted. A delivery failure (a handler that raises, `emit`, the logger) is logged with the class name only and cannot change the result (T9); the alert event itself is also always written to the log as `CHRONIS_DEV_ALERT`, which is existing behaviour of `alerts.emit`.
- `data_revision_id` is `HSSMResult.fit_dataset_hash` unless the caller gives one (`summarize_fit`, `make_summary`). UNKNOWN: whether the integration has another revision concept; if it does, the caller passes it and nothing else changes.
- Deduplication is per process: after a restart the first crash of a (user, stage, revision) alerts again.

## What would still be wrong (INFERENCE / UNKNOWN)
- UNKNOWN: the integration's call sites. `k_change = None` still means "no assessment was asked" (WP8 behaviour). If the integration drops the assessment record or never calls the assessment, the lineage cannot know; that is outside this package.
- UNKNOWN: which alert handlers the integration registers; the lineage only calls `alerts.emit_once`. With no handler the event goes to the log (existing behaviour of `alerts.py`).
- The bounded dedup memory can forget a very old (user, stage, revision); the consequence is one repeated alert, never a changed result.
