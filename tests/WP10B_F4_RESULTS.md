# WP10B F4 results (2026-11-27): the CPU-dependent drift stream and the skipped kernel test

Every number: Python 3.12.3, repo pins (numpy 2.2.6, OpenBLAS bundled with the wheel), one 2-core AVX-512 machine (default OpenBLAS kernel SkylakeX). I have no AMD EPYC 7763: what I say about it is INFERENCE from forced kernels here. Criteria: `tests/PREDECLARED_CRITERIA_WP10B.md` section 13, committed (ddafe47) before any test was changed.

## 1. Which function gives CPU-dependent numbers (RUN: `integration_report/wp10b/scripts/f4_generator_probe.py`, `wp10b_evidence/f4_generator_probe.txt`)
**`np.linalg.norm` of a 1-D float64 vector.** numpy computes it as `sqrt(x.dot(x))`, and `dot` is OpenBLAS `ddot`; the OpenBLAS kernel changes its last bit. It is called at two places in `data/synthetic_identity.py`: `_unit` (line 82; the drift and split directions) and the drift block of `generate_identity_stream` (line 151).
- opa's hash is reproduced here: seed 9996, `drift_sd = 1.0`, gives `d66af22924722a01` under a forced HASWELL, ZEN (reported as Haswell by this OpenBLAS) or NEHALEM kernel and `41355ac8122f9a17` (the WP8 hash) under the default SkylakeX kernel or a forced SKYLAKEX. The default, split and merge streams and both seed 9997 drift hashes are identical in every configuration.
- It is NOT numpy's AVX-512 dispatch (the F2 cause): switching that off changes none of the eight streams.
- The traced norms differ by one unit in the last place (1.3832449567254312 against 1.3832449567254315 at the first `_unit` call of seed 9996). 13 of the 1050 values of the 9996 drift stream differ, by at most 9.1e-13 absolute and 2.5e-16 relative.
- With the norm replaced by an exactly rounded one (`sqrt(fsum(x*x))`) the eight streams are bit-identical across the default, HASWELL and NEHALEM kernels (test `test_the_blas_norm_is_the_only_cpu_dependent_function_of_the_generator`), so nothing else in the generator depends on the kernel. For this probe vector the exactly rounded norm equals the Haswell / Nehalem value: the WP8 hash is the AVX-512 kernel's result and the AVX2 kernels give the correctly rounded one (one vector; not a general claim).

## 2. Is the same function used in the production fit, or only in the simulator?
**The same function is used in production, and BLAS in general is (READ).** `np.linalg.norm` of a 1-D array: `lineage.separation_min` (line 258; this is the identity gate `min_separation`), `shrinkage.py` line 195 (a diagnostic), `attractors/detector.py` line 42. `np.linalg.norm(..., axis=1)` (`label_switching.py`, `neural_residual.py`, `detector.py` line 67) is computed by numpy itself and does not use BLAS. The fit uses BLAS `dot` and `@` in `model.py`, `dual_model.py`, `shrinkage.py` and others.
**What it does there (RUN):** the lineage battery (384 records, `lineage_battery.py compare --tolerant`) gives the SAME discrete outputs (states, reasons, names, flags) under the Haswell and Nehalem kernels as under the default kernel in all 384 records; 80 records have a float that differs, all of them `separation_min`, by at most 2.6e-16 relative. The WP10A cross-kernel test, which fits the baseline and dual fixtures under three kernels, passes here (discrete outcomes identical; healthy fits within a relative 1e-8, observed 1.5e-11 in WP10A; not-converged fixture within 5e-2). INFERENCE: a one-bit difference in `separation_min` could change the gate only if the value sits within about 3e-16 of `min_separation`; I did not look for such a user and none of the 384 records flipped. Bit identity across kernels is not claimed for the production fit (WP10A A2: 300 of 655 stored fields differ) and cross-machine reproducibility is not claimed.

## 3. The skipped test, and the 7763
`test_the_forced_kernels_are_really_three_different_ones` skipped when the machine had fewer than three distinct OpenBLAS kernels. INFERENCE for the 7763: this OpenBLAS maps ZEN to its Haswell kernel (forcing ZEN here reports "Haswell"), so on a Zen 3 machine the default kernel is the Haswell one, default and forced HASWELL coincide, and only two distinct kernels (Haswell, Nehalem) exist. Replaced by a deliberate condition (`f4_lib.kernel_condition`): the two forced kernels must be honoured and be different (HASWELL gives "Haswell", NEHALEM gives "Nehalem"); the machine is then `three_distinct` or `default_is_a_forced_kernel`, recorded as a test property; a forced kernel that is not honoured FAILS; the only skip left is a machine that is not x86-64 (the skip text says so). A new test compares HASWELL against NEHALEM (healthy 1e-8, not-converged 5e-2, discrete outcomes identical), which carries the cross-kernel claim on every x86-64 machine, including one where default and forced HASWELL are the same kernel. RUN: a simulation of such a machine (the "default" child started with `OPENBLAS_CORETYPE=HASWELL`) passes and records `default_is_a_forced_kernel` (`wp10b_evidence/f4_controls.txt`). The first run on a real 7763 settles the INFERENCE.

## 4. The failing test
`test_default_streams_are_bit_identical_to_wp8` is changed (criteria 13.2(3)). A stream whose hash equals the WP8 hash passes as before. Otherwise it passes only if (a) the kind is `drift` or `split`, (b) this machine's norm of a fixed probe vector (the first `_unit` vector of seed 9996) differs from the WP8 value, and (c) the stream equals the stored WP8 array (`tests/data/wp8_identity_streams.npz`, checked against the WP8 hashes on load) within a relative 1e-15. `default` and `merge` must always be bit-identical; a machine with the WP8 kernel must reproduce the hashes exactly. The generator and the WP8 / WP9 / WP10A streams are NOT changed. RUN: the old test under a forced HASWELL kernel fails on exactly `[9996-drift]` as on opa's machine; the new one passes under default, HASWELL and NEHALEM; a corrupted stored reference is refused (`f4_controls.txt`).
