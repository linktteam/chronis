# HSSM integration contract (WP6 item 1)

For the owner's integrated pipeline. It states what `backbone.hssm` accepts, returns and raises, and what the product layer may read. Labels: **READ** = taken from the code, **RUN** = checked by a test or a run. Module paths under `backbone/hssm/` are stable; do not rename or move them. Companion: `docs/backbone/HSSM_RESULT_SCHEMA.md` (field-by-field).

## 1. Entry points

| Function | Module | Use |
|---|---|---|
| `fit_hssm(matrix, ...)` | `backbone.hssm.fitting` | The canonical fit; returns an `HSSMResult`; never raises for withheld insights. |
| `fit_hssm_gated_result(X, ...)` | `backbone.hssm.gating` | Same fit, legacy argument names, returns the `HSSMResult`. |
| `fit_hssm_gated(X, ...)` | `backbone.hssm.gating` | Legacy `(model, run_log)`; raises `InsightsWithheldError` when withheld; baseline model only. |
| `fit_with_random_restarts`, `fit_dual_with_random_restarts`, `select_k_by_bic` | `backbone.hssm.fitting` | Building blocks; the same input checks apply. |

## 2. Inputs (`fit_hssm`)

* `matrix`: `(T, F)` float array or DataFrame, one row per day (or per session), **z-scored per person by the caller** (the engine does not standardise; its initial variances come from the data and its variance floor is absolute). NaN is allowed: a row with at least 50% of its features observed is a *present session*; a row with every feature NaN is marginalised (contributes nothing, never imputed). `F >= 1`. (The legacy `fit_hssm_model` refuses NaN.)
* `timestamps` (optional): **calendar DAYS**, one value per row, finite, strictly increasing, fractional days allowed but no two rows on the same calendar day after rounding to whole days, span at most `MAX_TIMESTAMP_SPAN_DAYS` = 20,000 days. Seconds or milliseconds raise `ValueError` before any allocation (RUN: `tests/test_wp6_item1_timestamp_guard.py`). A unit mistake under the limit (hours over a month) is not detectable: the caller owns the unit. The baseline model uses the timestamps to put rows on a daily lattice (gaps become NaN rows; durations are in days); the dual-timescale model does **not** build a lattice: it works in row steps and uses the timestamps only to label `duration_unit` (READ).
* `candidate_ks` (default `(2, 3, 4)`), `n_initializations` (default 10, minimum 10 unless `allow_fast_test_fit=True`), `max_iter` (default 200), `max_duration` = Dmax (default 45, in lattice steps), `random_seed` (restart seeds are `random_seed + k*1000 + i`, and `+ i*31` for the dual model; READ), `model_type` (`"baseline"` or `"dual_timescale"`), `latent_dim` (dual only, default 2).
* `user_id`, `dataset_hash`: opaque strings copied into the result. The library neither computes nor verifies the hash (`HSSMFitDataset` computes one). `n_present_sessions`: optional override of the count used for the gate and for BIC.
* `config`: `ColdStartConfig(min_present_sessions=30)`.
* `shared_prior`, `shared_prior_n0`: optional, dual model only (WP5; schema section 3b).

## 3. Cold-start gate

Fewer than 30 present sessions: `ColdStartError`, nothing is fitted, no output (the correct silent state, not a low-confidence result). The timestamp check runs first, so a malformed argument raises `ValueError` even for a too-short record. The threshold is not changed by anything in WP5 or WP6.

## 4. Outputs

`HSSMResult` (schema sections 2 to 3b). The fields a pipeline needs: `fit_state` (`CONVERGED`, `MAX_ITER_REACHED`, `REJECTED_UPDATE`, `NUMERICAL_FAILURE`, `FAILED`, `MODEL_SELECTION_CONTESTED`), `K`, `BIC`, `AIC`, `p_t_estimate` / `p_t_posterior` (`(T, K)`; baseline: computed on the rows as given), `m_t_posterior_mean` / `m_t_uncertainty` (dual only; `None` for the baseline), `duration_parameters`, `fit_degraded`, `run_log` (one dict per restart), `convergence_metadata`, `eligible_session_count`, `calendar_start` / `calendar_end`, `used_shared_prior`.

## 5. Hold-back contract

The product layer reads regime and latent outputs **only** through `result.publishable_outputs()` (or the aliases `p_t`, `regime_posterior`, `m_t`), which return `None` when `result.insights_withheld`. The raw fields stay readable for diagnostics and must not reach a user. `result.withheld_reason` lists every cause. Rules in force (schema section 3): `fit_degraded`, `fit_state == NUMERICAL_FAILURE`, a fallback firing in the `estimate_states` pass, a fallback firing after the result was built, and, since WP6 item 3 (P0-07), two more:

* **`fit_state_not_converged`**: the fit state is `MAX_ITER_REACHED`, `REJECTED_UPDATE`, `FAILED` or `RUNNING`. A fit that did not converge is never publishable. `MODEL_SELECTION_CONTESTED` is a model-selection state of a fit that converged: it is judged by the fit's own state in `convergence_metadata["fit_state"]` (a result without that key counts as converged), so a contested result stays publishable. The dual-timescale model at the default 200 iterations did not converge in any of the 20 diagnosis users (`tests/WP6_CONVERGENCE_DIAGNOSIS.md`), so its results are withheld by this rule unless its stopping rule certifies them (see "Changes in WP6 item 3").
* **`collapsed_regime`**: the selected baseline fit has a regime with fewer than `COLLAPSE_MIN_EFFECTIVE_DAYS` = 4 effective days (`fit_collapsed`, details in `collapse_report`). A variance at the variance floor is reported (`n_variance_at_floor`) but does not by itself withhold: in the diagnosis such fits label no worse than healthy ones.
* **`degenerate_duration`** (WP7-R item 5, dual model): see 9.2. A `collapsed_regime` rule for the dual model was added in the same item (same threshold, computed from the filtered regime posterior).

## 6. Exceptions a caller can see

| Exception | Raised by | When |
|---|---|---|
| `ValueError` | `fit_hssm`, `fit_with_random_restarts`, `fit_dual_with_random_restarts`, `GaussianHSMM` | `F <= 0`; fewer than 10 restarts without `allow_fast_test_fit`; invalid `timestamps` (not numeric, wrong length, NaN or infinite, not strictly increasing, span over the limit, two rows on one calendar day); a shared prior that does not match the request, is not aggregate-only, or a strength without a prior; empty or non-positive `candidate_ks`; NaN in `fit_hssm_model`; K, F or L not positive when a model is built. |
| `ColdStartError` | `fit_hssm`, gated functions | Fewer than `config.min_present_sessions` present sessions. |
| `FittingConvergenceError` | `fit_with_random_restarts`, `select_k_by_bic`, `fit_hssm` | Baseline: none of the restarts of any candidate K ended `CONVERGED`. Dual: no restart finished (a shared-prior fit that did not finish). This is what the owner's run hit on 73 days. |
| `InsightsWithheldError` | `fit_hssm_gated` only | The fit finished but its insights are withheld; carries `reason` and the full `result`. |
| `InternalStateError` | engine | An internal invariant was violated (a log-likelihood that is `None` after a pass; canonicalisation postcondition). A bug, not an input problem. |
| `NotFittedError` | models | A fitted-only attribute is read before `fit()`. |
| `PriorBuildError` (an `HSSMError`) | `build_shared_prior` in `backbone.hssm.shrinkage` | The shared prior cannot be built: fewer usable users than the minimum, no healthy reference fit, or too few users survive the alignment rounds. NOT raised by `fit_hssm` (WP5; READ). |
| `MemoryError` | numpy | Not covered by any guard other than the timestamp span; the lattice is `T_grid x K x Dmax` float64 per array. |

Warnings: a `UserWarning` is emitted when the duration optimiser falls back; a `print` line when the baseline monotonicity guard fires (READ). Internal log: one WARNING per withheld result on logger `backbone.hssm.fitting`.

## 7. Known limitations that matter to an integrator (READ, not hidden)

1. The two models read time differently (section 2). For the dual model `duration_unit_source` says `"calendar_days"` when timestamps are passed although its durations are in row steps.
2. For the baseline model with timestamps, `fit_hssm` computes `p_t` on the rows as given, not on the daily lattice the model was fitted on.
3. `MODEL_SELECTION_CONTESTED` (two BICs within 2.0) is a `fit_state` of its own and is not a convergence failure.
4. The reported `m_t_uncertainty` omits parameter uncertainty (N17: coverage of +-2 sd 0.68 against 0.95 nominal in the WP5 study); it must not be presented as a calibrated interval.
5. Cold-start personal fits are weak on short records; the optional shared prior (WP5) helps on synthetic populations only.

## 8. Changes in WP6 item 3 (convergence and M-step health)

* **Baseline guard repair.** The EM monotonicity guard used to end a fit as `REJECTED_UPDATE` whenever the log-likelihood fell by more than 1e-4. In the diagnosis the cause was the duration M-step in 138 of 138 events (it could lower its own expected log-likelihood). Now, at the first such event the previous M-step is redone with a safeguarded duration update (it cannot lower that block's expected log-likelihood), the fit goes on, and the update is used for the rest of that fit. The event is recorded: `model.guard_repairs_` / `result.guard_repairs` (count) / `convergence_metadata["guard_repairs"]` (iteration and drop). If the repaired update still lowers the log-likelihood the fit ends `REJECTED_UPDATE` as before. Fits that never meet the guard condition are bit-identical to the WP5 code. The guard tolerance is unchanged (1e-4 baseline, 1e-3 dual).
* **Collapse.** `collapse_report` (`result.collapse_report`, `convergence_metadata["collapse"]`): effective days per regime (in the model's canonical regime order), the minimum, the number of variances at the floor, the threshold, `collapsed`. Restart selection (`fit_with_random_restarts`) takes the best converged restart that is not collapsed; only if every converged restart is collapsed does it return the best one, flagged and withheld. `select_k_by_bic` demotes a collapsed candidate K like a degraded one. This changes the selected fit only where the old best-log-likelihood restart (or BIC-best K) was collapsed; the diagnosis found no change in label accuracy from it (paired -0.0015, se 0.0087), so it is a safety rule, not an accuracy rule.
* **Multi-start summary (ledger N1).** `result.restart_summary` / `convergence_metadata["restart_summary"]` / `model.restart_summary_`: restarts run, converged, rejected, at the iteration limit, collapsed among the converged; how many converged restarts lie within 1.0 nat of the selected one; the adjusted Rand index of the other converged non-collapsed restarts' labellings against the selected one (list, median, minimum), how many are the same solution (index at least 0.9), and the log-likelihood gap to the best restart that is a different solution (`None` when there is none, and all comparison fields are empty when the selected fit is collapsed). Descriptive: nothing is withheld because of them. The run log carries `collapsed`, `min_effective_days`, `n_variance_at_floor`, `guard_repairs` for every restart.
* **Dual-timescale restart selection** prefers a converged restart to a non-converged one with a higher log-likelihood (the latter would be withheld).
* **Dual stopping rule at the iteration limit (C2).** The existing rule (`|ll - previous| < tol`) is unchanged and ends the fit `CONVERGED` with `convergence_criterion_ = "abs_tol"`. If the iteration limit is reached instead, the fit is certified `CONVERGED` (`convergence_criterion_ = "window_gain_at_cap"`) only if the log-likelihood gained less than `DUAL_CAP_CERT_GAIN_PER_ROW` = 2.0e-4 nats per row over the last `DUAL_CAP_WINDOW` = 10 iterations (`window_gain_at_cap_` holds the gain, also when it does not certify); otherwise it stays `MAX_ITER_REACHED` and the result is withheld (P0-07). `n_iter_` is now the number of iterations run (it used to stay 0 at the limit). In the diagnosis 10% of dual fits at the default 200 iterations met the certification rule, so **about 90% of dual fits at the default `max_iter` are withheld**; a larger `max_iter` or an accelerated EM would raise that share (not done in WP6). Evidence: `tests/WP6_CONVERGENCE_DIAGNOSIS.md`, addendum Q4b: a certified fit kept its regime labels (at most 0.62% of rows changed) and its `m_t` within 0.1 sd over 200 further iterations.
* **Dual duration box (D1).** The duration update could run to a flat, meaningless optimum (sigma at the optimiser wall 10, mu from -165 to 146, in 10 of 40 regimes of the diagnosis fits). `DualTimescaleHSSM.fit` now runs the fit as before and, only if it ENDS with a regime duration outside the box (mu in [-5, ln(10 Dmax)], sigma at most 3, finite), runs it once more from the same starting point with the box active (an update that leaves the box is redone from the previous iterate with a penalty outside the box). A fit that ends inside the box is never touched (bit-identical). The first fit is described in `model.duration_box_refit_` and `convergence_metadata["duration_box"]["first_fit"]`; `convergence_metadata["duration_box"]` also carries `refit`, `n_applications` and `applied` (iteration, regime, from and to values of every redo of the final fit); `result.duration_at_bound[k]` is True when regime k's final duration is within 1e-3 of a wall of the box (a regime whose best unconstrained pmf needs sigma above 3 loses a little log-likelihood; that is what the flag reports). A fit that is refitted costs about twice the time. Nothing is withheld because of the box. Switch: `DualTimescaleHSSM.DURATION_BOX_REFIT` (class attribute, default True).

### 9.1 Every `FitState` value

`result.fit_state` (and `convergence_metadata["fit_state"]`, which keeps the MODEL's own state) takes one of these values. The caller never needs to branch on the state to stay safe: `result.publishable_outputs()` already returns `None` whenever `insights_withheld` is True. The table says what each state means and what to do with it.

| `FitState` | Meaning | Withheld? | What the caller does |
|---|---|---|---|
| `CONVERGED` | The EM stopped by its rule. Baseline: `|ll - previous| < tol`. Dual: `convergence_criterion_` is `"abs_tol"` (same rule) or `"window_gain_at_cap"` (certified at the iteration limit, section 8). | No, unless another hold-back rule fires (9.2) | Read outputs only through `publishable_outputs()`. |
| `MAX_ITER_REACHED` | The iteration limit was reached and the fit is not certified. This is the normal outcome of the dual model at 200 iterations (9.5). | **Yes**, `fit_state_not_converged` | Show nothing. A larger `max_iter` may change the state (9.5); otherwise treat the record as "no model yet". |
| `REJECTED_UPDATE` | The monotonicity guard stopped the fit (the log-likelihood fell by more than 1e-4 baseline, 1e-3 dual) and, for the baseline, the one repair of WP6 did not cure it. | **Yes**, `fit_state_not_converged` | Show nothing; the details are in `run_log` and `convergence_metadata["guard_repairs"]`. |
| `NUMERICAL_FAILURE` | The Cholesky / covariance fallback fired in the fit, or the fit hit a numerical error. | **Yes**, `fit_state is NUMERICAL_FAILURE` (the dual also sets `fit_degraded`) | Show nothing; the data are probably degenerate (a constant feature, too few usable rows). |
| `FAILED` | The fit raised or produced no model (the value a model has before `fit()` and after a failed one). | **Yes**, `fit_state_not_converged` | Show nothing. Most cases raise `FittingConvergenceError` instead of returning (section 6). |
| `RUNNING` | Internal, transient state of a fit in progress. | Treated as not converged | `fit_hssm` does not return it; if a stored result carries it, treat the fit as failed. |
| `MODEL_SELECTION_CONTESTED` | Baseline path only: the two lowest BICs over the candidate Ks differ by less than 2.0 (and a held-out score could be computed). It replaces `result.fit_state`; the model's own state stays in `convergence_metadata["fit_state"]`. | Judged by `convergence_metadata["fit_state"]` (a result without that key counts as converged) | Publishable if the model's own state is `CONVERGED`. Do not present the chosen K as settled; the BICs are in `convergence_metadata["bic_by_k"]`. |

### 9.2 Withheld semantics (one place)

`result.insights_withheld` is True exactly when `result.withheld_reason` is not `None`; the reason is a `"; "`-joined list of EVERY cause, each starting with one of these prefixes:

| Prefix | Fires when | Applies to |
|---|---|---|
| `fit_state_not_converged` | the (underlying) fit state is `MAX_ITER_REACHED`, `REJECTED_UPDATE`, `FAILED` or `RUNNING` | both models |
| `collapsed_regime` | a regime has fewer than `COLLAPSE_MIN_EFFECTIVE_DAYS` = 4 effective days (strictly below; column sum of the regime posterior) | both models. Baseline: the smoothed posterior on the daily grid. **Dual (WP7-R item 5, R1): the FILTERED `p_t_posterior` the result carries (the dual model returns no smoothed regime posterior); `fit_collapsed` and `collapse_report` (with `source = "filtered_regime_posterior"`) are now filled for the dual result.** |
| `degenerate_duration` | **dual only (WP7-R item 5, R2):** a regime's duration parameters are at a wall of the duration box (`duration_at_bound`: mu or sigma within `DUAL_DURATION_BOUND_TOL` = 0.001 of a wall, which includes sigma at its wall 3.0) OR its duration pmf (truncated lognormal on 1..Dmax) is still RISING at the last lattice step (`pmf[Dmax] > pmf[Dmax-1]`, i.e. the mode lies beyond Dmax) | dual; fields `fit_duration_degenerate` and `duration_degenerate_report` (per regime `at_bound`, `pmf_rising_at_end`, `degenerate_regimes`, `Dmax`) |
| `fit_degraded` | the -1e6 Cholesky fallback fired during `fit()` | dual |
| `fit_state is NUMERICAL_FAILURE` | the fit state is `NUMERICAL_FAILURE` | both |
| `states_pass` | the fallback fired in the `estimate_states` pass of `fit_hssm` | dual |
| `late_fallbacks` | the fallback fired on the model after the result was built | dual |

A fit can be withheld although its state is `CONVERGED` (collapse, a degenerate duration, degradation, a fallback). Since WP7-R item 5 a dual fit that ENDS with a degenerate duration (the `degenerate_duration` row) is withheld: the duration box (section 8) still refits a fit that leaves the box first, and the result is judged on the fit that remains, so a regime that ends at a wall of the box, or whose duration law is still rising at the lattice end, is not publishable. `duration_at_bound` stays metadata; `fit_duration_degenerate` is the rule. The usual cause is a regime segment longer than `Dmax` (Item 1, RE-VERIFIED: Fisher p = 0.0009; `Dmax = 60` cured 8 of 9 such fits): see 9.9 for the opt-in retry. The raw arrays stay readable for diagnostics and must not reach a user; the aliases `p_t`, `regime_posterior` and `m_t` follow the same rule as `publishable_outputs()`.

### 9.4 What `HSSMResult` does not contain

There is **no per-session confidence** in `HSSMResult` (RUN: the smoke script and a doc test check that no field named `confidence`, `session_confidence` or `p_t_confidence` exists). `p_t_posterior` is the filtered regime posterior of the fitted model (the model's own probability given its parameters, not a calibrated confidence). `m_t_uncertainty` (dual) is a posterior standard deviation that leaves out parameter uncertainty: in the WP6 evaluation the +-2 sd band covered 0.716 of the truth (nominal 0.9545) and the Hessian-term prototype reached 0.818 (`tests/WP6_N17_RESULT.md`), and it was not integrated. It must not be shown as a calibrated interval. `restart_summary`, `collapse_report` and `convergence_metadata` describe the FIT, not a session. Until N17 passes the product shows no numeric confidence derived from these fields.

### 9.5 `max_iter` guidance (RE-RUN from `wp6_evidence/recovery_after.jsonl`, WP6 item 4; K = 3, F = 7, T = 75 baseline designs B-F2 and B-F3, 24 datasets x 10 restarts each, after the WP6 repair)

* **Baseline:** all 480 restarts converged. Iterations to convergence: median 16 (B-F2) and 15 (B-F3), 90th percentile 26 and 27, maximum 93 and 63; 98.75% and 99.58% of the restarts converged within 60 iterations and all within 100. The integration run used `max_iter = 60`: enough for about 99% of restarts on data like this; a restart that needs more ends `MAX_ITER_REACHED` and is skipped. The default 200 is the safe choice (a converged restart stops early, so the higher limit costs nothing). Wall time of a 10-restart baseline fit at T = 75: 3.6 to 5.9 s mean in the WP6 runs (contended cores).
* **Dual-timescale:** 200 iterations are NOT enough. In the WP6 item 4 population run 22 of 24 dual fits ended `MAX_ITER_REACHED` at `max_iter = 200` and were withheld (2 certified by the window rule); mean wall time 76 s per fit on contended cores (range 37 to 170 s). In the WP6 diagnosis every one of the 44 dual fits (30, 100 and 200 iterations) ended `MAX_ITER_REACHED` and was still rising (`tests/WP6_CONVERGENCE_DIAGNOSIS.md`, point 7). How many iterations a dual fit needs is not established by this contract (WP7-R item 1 looks at it from the prediction side); the dual-timescale model remains a research engine, not a pilot engine.

### 9.6 Corrections to earlier statements (READ against the WP6 evidence; nothing in the code changes)

* Section 8 (dual stopping rule) says a certified fit kept its labels and its `m_t` within 0.1 sd over 200 further iterations (diagnosis addendum Q4b). The WP6 item 4 check on the two fits that WP6 actually certified (seeds 7204, 7221; `wp6_evidence/summary_item4_recovery.txt`, line S5) measured a largest `m_t` change of 0.29 sd and 2.24 sd, with 0 and 0.39% of the labels changed, and the continuation fits themselves were still `MAX_ITER_REACHED` at 200 and at 400 further iterations. So `window_gain_at_cap` is a weaker certificate than `abs_tol`: it supports the labels, not a tight `m_t`.
* Section 7, item 4 quotes N17 coverage 0.68 (WP5 study); the WP6 evaluation measured 0.716 (E0) at +-2 against 0.9545 nominal. Both say the same thing: the reported `m_t_uncertainty` is too narrow.

### 9.7 Integrator checklist

1. z-score each person's matrix yourself; 2. pass calendar DAYS as `timestamps` (span at most `MAX_TIMESTAMP_SPAN_DAYS` = 20,000; seconds raise `ValueError`); 3. at least 30 present sessions or `ColdStartError`; 4. at least 10 restarts, default `max_iter` 200 (60 is enough for about 99% of baseline restarts); 5. read regime and latent outputs only through `publishable_outputs()`; 6. show no numeric confidence; 7. treat the dual model as research only.

### 9.8 BIC parameter count and model selection (WP7-R item 2, P1-01)

`GaussianHSMM.n_params()` (used by `bic()`, `aic()` and therefore by the choice of K in `fit_hssm`) counts `(K-1) + K(K-1) + 2KF + 2K` parameters. The transition term over-counts: the M-step keeps a zero diagonal (dwell time lives in the duration law), so each row has K-1 non-zero entries that sum to 1, i.e. `K(K-2)` free entries (K = 2: none). The count is too large by **K**, so the BIC penalty is too large by `K*ln(n)` (n = present sessions). **Since WP8 (owner decision B1) the default is the free count** (`GaussianHSMM.n_params_convention = "free"`); the old count stays selectable (`n_params_convention = "legacy"`, a class or instance attribute) for anyone who needs to reproduce an older selection. In the WP7-R study (48 simulated datasets, T = 75, F = 7, K in {2, 3, 4}) the free count changed the selected K in 0 datasets (`tests/WP7R_ITEM2_RESULTS.md`), and re-running those 48 datasets through `fit_hssm` with the new default gave the same selected K in every one (`tests/WP8_ITEM0_RESULTS.md`). The same study shows that BIC can **under-select K** when regimes overlap (planted K = 3 and 4 were served as K = 2 in 15 of 16 hard-design datasets, all served, none withheld): a served K is not evidence that the person has exactly that many regimes.

### 9.9 Dual honesty rules and the opt-in Dmax retry (WP7-R item 5)

Design and reasons: `tests/PREDECLARED_CRITERIA_WP7R.md` section 5 (written before the code); tests `tests/test_wp7r_item5_dual_honesty.py`. Two rules were added for the DUAL model and one opt-in option; the baseline model, every default and every numeric output of a fit are unchanged (the rules change whether a fit is publishable, nothing is recomputed).

* **R1 `collapsed_regime` (dual).** Effective days of regime k = the sum over rows of `p_t_posterior[:, k]` (the FILTERED posterior, causal, the one the result carries). The fit is collapsed iff the minimum over regimes is strictly below `COLLAPSE_MIN_EFFECTIVE_DAYS` = 4.0 (the baseline constant; the 4-day rule is not changed here). `collapse_report["source"] = "filtered_regime_posterior"` marks it; for the baseline the report is computed from the smoothed posterior on the daily grid.
* **R2 `degenerate_duration` (dual).** See the row in 9.2. No threshold beyond the existing box tolerance: a pmf that is still rising at the last lattice step has its mode beyond `Dmax`, so the fitted duration law is truncated.
* **R3 `max_duration_retry` (opt-in, default `None`).** `fit_hssm(..., model_type="dual_timescale", max_duration=D, max_duration_retry=D2)` with an integer `D2 > D`, dual model without a shared prior (otherwise `ValueError`). If the selected dual fit ends degenerate (R2), the selected K is fitted once more with `max_duration = D2` (same seeds, restarts and iterations). The retry REPLACES the first fit only if it is not degenerate; otherwise the first fit is kept and is withheld. `convergence_metadata["dmax_retry"]` records `requested`, `from`, `first_fit_degenerate`, `adopted` and `retry_fit_state`; the retry's run log entries carry `dmax_retry = True`; when adopted, `Dmax`, `BIC` and `duration_degenerate_report["Dmax"]` describe the retry. Cost: one more fit for a degenerate fit and none otherwise; a fit that is not degenerate is bit-identical to the same call without the option. The default `Dmax` is NOT changed: a larger lattice changes the model class and the run time, and 8 cured fits of 9 is a development-size number.
* **Not done:** a held-out "publish gate" for the dual model (WP7-R item 5c): Item 1 found no consistent decline of the held-out score with more EM, so it was not built.

### 9.10 Regime identity across refits (WP8 Item 4)

Raw regime ids are **not stable across fits** (refit on a longer window, another seed, or the other engine and the same regime gets another id; the baseline's raw order is a label convention, not an activity order: `backbone/hssm/label_switching.py`). `backbone/hssm/lineage.py` adds a second set of names and says how far they can be trusted. The raw record is never changed (owner decision A4); `HSSMResult.lineage` (default `None`) carries the lineage record after the application calls `lineage.annotate_result(result, record)`. Pure functions: `summarize_fit`, `step`, `apply_user_choice`, `may_claim_same_as_before`.

* **What the caller must do.** Keep the `LineageState` per user (it is immutable: `step` returns a new one), feed every ACCEPTED fit (`not insights_withheld`) of either engine to `step(state, summarize_fit(result, raw_window, scaler_mean, scaler_std), config, registry, lineage_id=...)`, where `raw_window` is the window in physical units and the scaler is the one that z-scored it for the model. Store the returned record next to the raw result.
* **"Same as before" is allowed only when `continuity_state == "ALIGNED"`** (`may_claim_same_as_before`; fail closed). `NEW_LINEAGE` is a first fit or a fit whose names the user chose; it is not a claim of continuity. On `CONTINUITY_UNVERIFIED` and `K_CHANGED` the OLD names are kept, `message` says "cannot confirm this is the same as before", and `proposed_new_names` holds the alternative; the user's answer goes through `apply_user_choice` (`NEW_NAMES` starts a new epoch and stores the old-to-new mapping in `LineageState.epoch_history`; `None` and `KEEP_OLD` leave the old names; no response means `None`).
* **Stable names** come from the ordering ladder (`backbone/hssm/ordering.py`) at a lineage's first accepted fit and are inherited by alignment afterwards. `activity_rung` 0 means the order could not be verified: ids follow first-fit order and **nothing about activity may be said**.
* **Alignment** compares regime means in raw physical units (the scaler of every fit is stored in its record), also across an engine switch. A fit whose regimes are too close to each other (`separation_min` below the gate `min_separation`) is not identifiable and can never be ALIGNED. Every record stores the margins (`margin_diff`, `margin_ratio`, best and second best cost, per-regime distances), also when the state is not ALIGNED.
* **Frozen numbers (Item 4 design freeze, 2026-11-25, from 960 development fits).** Gate `min_separation = 4.0`; baseline-to-baseline pairs: `margin_ratio <= 0.5` (the WP5 rule); **dual-to-dual pairs and baseline/dual switches have no calibrated threshold** (fewer than 20 development alignments passed the gate) and are **never ALIGNED**: state `CONTINUITY_UNVERIFIED`, reason `threshold_not_calibrated`, old names kept, margins recorded. On the development streams the frozen design serves 37% of baseline pairs as ALIGNED (all of them correct); the declared target was 80%, so most refits will say "cannot confirm this is the same as before". A lower gate serves more pairs and lets some wrong ones through (3.0: 63% served, 0.5% of all pairs wrong); this is a configuration choice (`AlignmentConfig.min_separation`) for the owner and the expert. Numbers, tables and the dated rule: `tests/PREDECLARED_CRITERIA_WP8.md` (section 8, Design freeze Item 4) and `tests/WP8_ITEM4_RESULTS.md`.
* **Open for an expert (owner decision A7):** the matching distance, the ladder weights and every threshold; every record carries `expert_review_status = "PENDING"` until the owner records a sign-off. Every place in `backbone/hssm/` that defines or uses them is tagged `EXPERT_REVIEW(identity-distance)`; `docs/EXPERT_REVIEW_REGISTER.md` lists every tagged site and the values under review, is generated by `integration_report/wp8/scripts/expert_review_register.py --write`, and `tests/test_wp8_item7_expert_review.py` fails when it is stale or when a function uses the distance, a ladder weight or a threshold without the tag.
* **Not done here:** the application's choice and any display (no UI).
* **Two channels (WP8 Item 5, owner decision A6).** Channel 1 is physical: regime means in real units with the stored scaler, readable through the feature registry (`feature_registry.FeatureSpec`: name, unit, source, role, activity direction; `lineage.regime_table`). Channel 2 is OPTIONAL and contextual: one non-negative profile per regime that sums to 1 (for example topic or scene proportions aggregated per day; `lineage.context_profiles_from_days` aggregates the caller's daily proportions by the decoded regime), supplied by the caller in `FitSummary.context_profiles`. It is off by default (`ChannelConfig.w2 = 0`: channel 1 alone, bit for bit); with `w2 > 0` the combined cost is `w1 * d1 / s1 + w2 * d2 / s2` (d2 = squared Hellinger distance, s = the anchor's mean distance between its own regimes in that channel), and **if each channel alone gives a confident alignment but the two assignments differ, the state is `CONTINUITY_UNVERIFIED`** (`reasons` contains `channels_disagree`). A missing profile makes the step fall back to channel 1 and the record says so (`channel_detail`). **Contextual descriptors are sensitive personal data: they must come from a consented, aggregated, non-identifying pipeline; this package contains no topic or scene extraction and never reads raw conversations or images.**
* **Refit cadence (WP8 Item 6, owner decision A5).** `backbone/hssm/refit_policy.py`: `RefitPolicy(refit_interval_days=7)` (default 7 days, weekly), allowed range **1 to 28** whole calendar days (below 1 the refit would see no new data; above 28 the gap between two aligned fits, and with it the drift of the regime means that an alignment has to bridge, grows beyond what the WP8 studies tested; the studies measure daily, weekly and every 14 days). `should_refit(last_refit_day, today, policy)` is a pure function (no clock); `RefitPolicy.from_config({"refit_interval_days": 14})` changes the cadence with a configuration change only. It says when a refit is due, not whether a user is eligible for a fit.

### 9.11 WP9 additions (all additive; a fit that does not use them is bit-identical to WP8, counts in `wp9_evidence/` and the report)

* **FIT_UNSTABLE (A1).** `HSSMResult.restart_summary` of a baseline fit gains six keys: `consensus_m` (3), `consensus_tau` (0.99), `n_healthy_restarts`, `consensus_min_ari`, `fit_unstable`, `fit_unstable_reason` (`fewer_than_m_healthy_restarts`, `best_restarts_disagree`, `stability_not_assessed`). Rule: the best three healthy restarts (CONVERGED, not collapsed; by log-likelihood) must agree pairwise at adjusted Rand index of at least 0.99. **Nothing about the selected model, the restarts or any published number changes: it is a flag.** `lineage.summarize_fit` copies it (`FitSummary.fit_unstable`, `fit_unstable_reason`; a baseline result without an assessment counts as unstable, fail closed). `lineage.step` never serves a flagged fit as ALIGNED (reason `fit_unstable`), and a flagged anchor blocks the next alignment (reason `anchor_fit_unstable`); the first unflagged fit after it becomes the new anchor with the best-guess names (that step stays `CONTINUITY_UNVERIFIED`). The dual engine has no multi-start consensus and its lineage is never ALIGNED (below). Design: `tests/PREDECLARED_CRITERIA_WP9.md` sections 6 and part 3.
* **K change (A3).** `backbone/hssm/k_change.py`. At a refit the caller may compute `k_change.assess_against_anchor(state, raw_window, seed=...)` (it fits the last `K_CHANGE_RECENT_DAYS` = 45 days at K_a - 1, K_a and K_a + 1 with the production fit, compares the BIC and returns a record) and pass it to `summarize_fit(..., k_change=record)` (additive; `None` = nothing known = WP8 behaviour). A suspected change (`record["suspected"] is True`, direction `up` or `down`, BIC margin at least `K_CHANGE_DELTA_UP` / `K_CHANGE_DELTA_DOWN`) with the SAME fitted K gives `CONTINUITY_UNVERIFIED` with the reason `k_change_suspected`: **the old names are kept and the record says "cannot confirm this is the same as before"** (`may_claim_same_as_before` stays False; the user may choose new names as before). A different fitted K stays `K_CHANGED`. `LineageRecord.k_change` carries the signal and the split / merge candidates from the posterior overlap with the old regimes (old regimes in raw and in stable ids); the old nearest-mean `split_merge_candidates` are still there. Fails closed: an unfinished or unaccepted recent-window fit means no signal, never a claim. Thresholds: `config.K_CHANGE_*`. Design and numbers: `tests/PREDECLARED_CRITERIA_WP9.md` part 7.
* **"Unsure number of phases" (B3).** `HSSMResult.k_adequacy` (baseline only; `{}` for the dual engine) and the property `HSSMResult.k_unsure`. Signals of the SELECTED fit: regimes overlap (smallest pairwise separation in within-regime sd, `config.K_ADEQUACY_MIN_SEPARATION`), another K within `K_ADEQUACY_BIC_MARGIN` BIC points or the selected K is the largest candidate (`K_ADEQUACY_FLAG_LARGEST`), restart disagreement (A1). **The best guess is still shown, the selected K never changes** (`best_guess_shown = True`). When `k_unsure` a developer alert is emitted: `backbone.hssm.alerts.emit("k_unsure", ...)` logs one WARNING on the logger `chronis.hssm.alerts` (JSON) and calls the registered handlers (`alerts.register_handler`); events carry `user_id_hash` (first 16 hex digits of SHA-256), K, reasons and numbers, never the user id or any data (forbidden keys are refused).
* **Cold-start certification (B1, opt-in).** `fit_hssm(..., certify_prior_anchored=True)` (dual model with a shared prior only; otherwise `ValueError`) fills `HSSMResult.certification` and, when the fit is prior-anchored and EM ended `REJECTED_UPDATE` or `MAX_ITER_REACHED`, tests it by rolling-origin held-out one-step prediction against a single Gaussian (margin in HAC standard errors, `config.COLD_START_CERT_Z`) and by parameter stability. State `CERTIFIED_PRIOR_ANCHORED` makes the fit publishable **only** when nothing else withholds it (`withheld_reason` drops `fit_state_not_converged` and nothing else; `fit_state` keeps EM's verdict); every other outcome is `NOT_CERTIFIED` with reasons, and an exception or a non-finite number is NOT_CERTIFIED. Costs three extra dual fits. Default off: a call without the option is unchanged. Design: part 5. **Evaluation (24 synthetic users, run once; `tests/WP9_B1_RESULTS.md`): at 30 / 60 / 120 steps the share of `shrink5` fits publishable by the EM rule was 7 / 8 / 9 of 24 and after certification 7 / 12 / 14 (0, 4 and 5 certified; all 27 certified fits of all arms predicted better than a single Gaussian). The cold-start gain "survives" sentence is NOT shown (30 steps not judged, n = 7) and the net deployment gain is NOT shown at 30 steps (mean - 3 se = -0.096). The two prior controls were not wrong priors on the evaluation seeds, so whether a harmful prior would be refused is UNKNOWN. z = 3.0 is the conservative N18 margin, not a calibrated one (no z met the declared development rule).**
* **Identifiability gate and posterior-sharpness floor (A2).** `AlignmentConfig.min_separation` (the gate h) is now **2.5** (WP8: 4.0), chosen by the declared rule on development seeds 9301..9360 (`tests/DESIGN_FREEZE_WP9_A12.txt`). A baseline fit whose mean maximum regime posterior is below `config.FIT_MIN_POSTERIOR_SHARPNESS` (0.95) is flagged FIT_UNSTABLE with reason `low_posterior_sharpness` (`lineage.fit_stability_flag`). Neither changes a fit; both change which lineage steps may be served as ALIGNED ("same as before"). The coverage numbers and whether the 80% / 1% targets are met are in `tests/WP9_A12_RESULTS.md`; development coverage was 45.9% (hard 5.6%, medium 47.2%, easy 85.0%) with 0 of 540 wrong-and-unflagged. **Evaluation (48 synthetic users, run once): coverage 49.5% (target 80%: NOT MET), wrong-and-unflagged 0 of 432 (target 1%: MET, upper bound 0.9%); identical lineage across two fit seeds among served 67.6% strict (target 95%: NOT MET; 82.6% with 20 restarts); no flagged fit was served (0 of 230).** 80% coverage and at most 1% wrong are not jointly reached on the generator's mix (only the easy stratum reaches both); with the consensus flag off coverage at the same gate is 77.1% with 0 of 432 wrong, and what to do about the flag is an open owner decision (`tests/WP9_A12_RESULTS.md`, `docs/EXPERT_REVIEW_PACKET.md` section 4).
* **Monitoring primitives (B5).** `backbone/hssm/monitoring.py`, pure functions, no UI. `predictability_monitor(scores)` returns events when the recent mean of a per-day held-out score falls below the trailing reference by a declared amount (`config.MONITOR_*`); `alert_on_drop(user_id, result)` sends one developer alert per event (hashed id, numbers only); `confidence_display_gate(calibrated_confidence, calibration_evidence)` returns `early_estimate` unless N17 has passed (`config.N17_PASSED`, **False**), calibration evidence exists for the class of fit and the confidence is at least 0.85: **while N17 is not passed the gate returns `early_estimate` for every input**. `baseline_predictive_increments(model, X)` gives the held-out one-step scores of a fitted baseline model. Simulation result: `tests/WP9_B5_B6_RESULTS.md` (the monitor as declared does NOT meet its false-alarm level).
* **Re-certification of withheld fits (B6).** `backbone/hssm/recertify.py`. `recertify(X, new_rows, metadata=...)` refits with the production `fit_hssm` on the stored plus the new days and returns `PUBLISHABLE` only when the new result is not withheld by the existing publish rule; it has no parameter that loosens a rule and refuses settings that would (fast-test fit, fewer than 10 restarts, a lowered cold-start gate, unknown settings). `recertify_due` / `recertification_sweep` are the schedule hook (the refit policy, weekly by default); no clock or state inside.
* **Pairs of fits with no calibrated threshold (A6, unchanged in WP9; engine reliability is WP10).** Dual to dual, baseline to dual and dual to baseline pairs are **never ALIGNED** (`PairThreshold.calibrated = False`, reason `threshold_not_calibrated`): the WP8 development data had too few gate-passing alignments of those classes (4 of 216 and 16 of 480) to support a threshold. WP9 did not calibrate them and does not claim to.
